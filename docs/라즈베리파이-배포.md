# 라즈베리파이 엣지 제어기 배포

현장 제어함 안의 엣지 제어기로 라즈베리파이를 쓸 때의 설치·운영 기준이다.

## 자원 소요 — 실측

판단 1회는 모델 추론 하나가 아니다. 센서 입력 → 파생변수 → 시계열 피처 202개
→ 위험유형 4종 추론 → 복합위험 조합 → 판단근거 추출 → 조치 결정 → 이력 기록
전부를 거친다. 아래는 그 전체를 잰 값이다.

| 항목 | 측정값 | 측정 조건 |
|---|---|---|
| 판단 1회 | **29 ms** | 1코어 고정, 단일 스레드 |
| 판단 1회 | 34 ms | 1코어, 벤치마크 스크립트 |
| 판단 1회 | 38 ms | 4코어 |
| 상주 메모리 | **181 MB** | 모델 8개 + 48시간 관측창 적재 후 |
| 최대 메모리 | 173 MB | VmHWM |
| 모델 파일 | 10.5 MB | LightGBM 텍스트 8개 |

**코어를 늘려도 빨라지지 않는다.** 1코어 34ms 와 4코어 38ms 가 사실상 같다.
이 작업은 단일 스레드에 묶여 있어서, 라즈베리파이에서는 **코어 수가 아니라
코어당 성능**만 본다.

> 위 값은 x86_64 서버급 CPU 기준이다. 라즈베리파이의 코어당 성능은 이보다
> 낮으므로 실제 제어기에서 반드시 다시 재야 한다. 다만 사업계획서 목표가
> '평균 30초 이내'이고 지금이 29ms 이므로, 코어당 성능이 수십 배 낮더라도
> 목표 안에 든다.

제어기에서 그대로 다시 재는 방법:

```bash
OMP_NUM_THREADS=1 python scripts/benchmark_inference.py \
    --cache artifacts/dataset.pkl --models artifacts/weather \
    --out artifacts/benchmark-pi
```

## 권장 사양

| 항목 | 권장 | 근거 |
|---|---|---|
| 모델 | Raspberry Pi 4 (4GB) 이상 | 상주 181MB 라 2GB 로도 돌지만, OS·수집기·웹서버가 함께 올라간다 |
| 저장장치 | **SSD (USB 부팅)** | microSD 는 로그·시계열 쓰기로 수명이 빨리 닳는다 |
| 전원 | UPS 경유 | 정전 중 쓰기가 끊기면 저장장치가 깨진다 |
| 냉각 | 방열판 + 팬 | IP65 함체 안은 여름에 온도가 오른다. 과열 시 클럭이 떨어진다 |
| OS | Raspberry Pi OS (64-bit) | LightGBM·numpy 휠이 aarch64 로 제공된다 |

사업계획서의 제어함 사양(IP65 600×500×250, 환기팬·결로방지 히터, UPS 600VA)이
이미 이 조건을 담고 있다.

## 설치

```bash
sudo apt update && sudo apt install -y python3-venv python3-dev
python3 -m venv /opt/ofdf/venv
/opt/ofdf/venv/bin/pip install -r requirements.txt

# 1코어에 묶는다. 스레드를 늘려도 빨라지지 않고 전력만 쓴다.
echo 'OMP_NUM_THREADS=1' | sudo tee /etc/default/ofdf

sudo cp deploy/ofdf-edge.service /etc/systemd/system/
sudo systemctl enable --now ofdf-edge
```

## 운영 중 확인

```bash
systemctl status ofdf-edge          # 동작 여부
journalctl -u ofdf-edge -f          # 실시간 로그
vcgencmd measure_temp               # 온도 (80℃ 넘으면 클럭 저하)
vcgencmd get_throttled              # 0x0 이 아니면 전원·발열 문제
```

## 통신이 끊겼을 때

사업계획서는 **로컬 72시간 독립운전**을 요구한다. 제어기는 서버 응답이 3분간
없으면 로컬 독립운전으로 넘어가 수집·판단·제어·기록을 계속하고, 판단 이력을
JSON Lines 로 쌓아 두었다가 복구되면 시간순으로 올린다
(`ofdf.action.journal`). 한 줄이 판단 하나라서 중간이 깨져도 나머지를 읽는다.

72시간치 판단 이력은 5분 주기 기준 864건, 한 건이 약 1.6KB 이므로 **1.4MB**
정도다. 저장공간은 문제가 되지 않는다.

## 화면 — 패널과 휴대폰은 다른 화면이다

하드웨어는 Shrimp365 수질 장비와 같다 — 라즈베리파이 + **공식 7인치 터치스크린
(800×480)**. 그 패널과 농가 휴대폰은 **다른 페이지**를 본다. 같은 자료
(`data.json`)를 읽지만 구성이 다르다.

| | 터치패널 `kiosk.html` | 휴대폰·PC `index.html` |
|---|---|---|
| 역할 | **보는** 화면. 3m 밖에서 지나가며 봐도 들어와야 한다 | **읽는** 화면. 앉아서 따져 보는 자리 |
| 구성 | 한 화면, 스크롤 없음. 알람 띠 · 큰 숫자 넷 · 할 일 두 줄 | 농가/운영자 전환, 위험 카드, 판단근거, 24시간 그래프, 센서 상태, 이력 |
| 바탕 | 어두움 (밤 제어함에서 눈부시지 않게) | 밝음/어두움 자동 |
| 조작 | 숫자 칸 탭 → 다음 넷. 그뿐 | 전환·펼침·스크롤 |
| 글자 | 숫자 44px, 제목 30px — 장갑 낀 손, 먼 눈 | 15px 본문 |

**말은 하나다.** 위험 이름·조치 문장·숫자 이름(`plain.js`)을 두 화면이 같이
쓴다. 패널에서 '비닐·부직포 덮기'라고 본 것을 휴대폰에서 '피복 전개'라고
읽으면 다른 일인 줄 안다.

라즈베리파이가 로컬에서 띄우므로 인터넷이 끊겨도 현장에서 볼 수 있다.

서비스는 **셋으로 나눠** 띄운다.

| 유닛 | 하는 일 | 왜 따로인가 |
|---|---|---|
| `ofdf-edge` | 5분마다 수집·판단·조치·기록, `data.json` 갱신 | — |
| `ofdf-dashboard` | `dashboard/` 를 8080 으로 제공 | **판단이 죽어도 화면은 살아서 '멈췄다'고 알려야 한다.** 한 프로세스면 같이 죽어 농가가 아무것도 모른 채 낡은 값을 본다 |
| `ofdf-kiosk` | 터치패널에 `kiosk.html` 을 전체화면으로 | 패널에만 필요하다. 휴대폰만 쓰는 구성에서는 안 깐다 |

```bash
sudo cp deploy/ofdf-*.service /etc/systemd/system/   # edge·dashboard·kiosk·rtl433·modbus
sudo systemctl enable --now ofdf-edge ofdf-dashboard
sudo systemctl enable --now ofdf-kiosk      # 터치패널이 붙어 있을 때만
```

농가 휴대폰은 같은 공유기에서 `http://<파이주소>:8080/` 으로 들어온다
(패널 화면을 휴대폰에서 보려면 `/kiosk.html`).
**포장 내부망 전용이다.** 공인 IP 로 8080 을 열지 않는다 — 인증이 없다.

### 화면이 스스로 지키는 것

- **30초마다 다시 읽는다.** 벽패널은 아무도 새로고침하지 않는다. 1회만
  읽으면 부팅 때 값에서 영원히 멈춘다.
- **15분 넘게 갱신이 없으면 빨간 띠를 띄운다.** 판단 주기 5분 × 3회 연속
  놓침이 기준이다. 서리가 내리는 밤에 사흘 전 '정상'을 띄우는 것이 이
  화면이 할 수 있는 가장 나쁜 일이다. 연결이 끊겨도 **마지막 값을 지우지
  않고** 낡았다고 적는다 — 빈 화면보다 낫다.
- **원격 글꼴이 렌더링을 막지 않는다.** 통신이 끊긴 포장에서 글꼴 하나
  기다리느라 위험 알림이 늦으면 안 된다. 못 받으면 시스템 글꼴로 간다.
  파이에 한글을 깔아 둔다: `sudo apt install fonts-noto-cjk`
- **터치 대상 48px 이상**(휴대폰 56px). 장갑 낀 손 기준이다.

### Zigbee 센서 연결

센서는 라즈베리파이에 꽂은 코디네이터(SONOFF Dongle)로 들어오고
Zigbee2MQTT 가 장치마다 JSON 을 MQTT 로 내보낸다. 그것을 수집 형식으로
바꾸는 것이 `scripts/zigbee_bridge.py` 다.

```bash
pip install paho-mqtt
python scripts/zigbee_bridge.py --devices configs/devices.yaml --out data/field
```

`configs/devices.yaml` 에 장치마다 **어느 구간에 달렸고 어느 변수인지** 적는다.

**센서는 여러 대 붙는다.** 사업계획서의 설계는 구간마다 초관부 온습도 2점·
토양수분·지온 2점(10·20cm)·엽면습윤 2점이고, 비교구간에 같은 구성을 대칭으로
둔다. 매핑을 장치마다 적으면 토양센서 넉 대에 같은 줄을 네 번 적게 되고
하나만 고치는 날이 온다. 그래서 **종류**(`kinds:`)에 매핑을 적고 장치에는
종류와 설치 위치만 적는다.

```yaml
kinds:
  canopy:
    map: {temperature: canopy_temp, humidity: rh}   # 지상 10cm 이므로 기온이 아니다
    sends: [battery, linkquality]
  soil:
    map: {temperature: soil_temp}
    sends: [soil_moisture, battery, linkquality]

devices:
  canopy-treat-01: {kind: canopy, zone: treatment, sensor_id: CN-T1, note: 이랑 동쪽}
  canopy-treat-02: {kind: canopy, zone: treatment, sensor_id: CN-T2, note: 이랑 서쪽}
  canopy-ctrl-01:  {kind: canopy, zone: control,   sensor_id: CN-C1}
  canopy-ctrl-02:  {kind: canopy, zone: control,   sensor_id: CN-C2}
  soil-treat-01:   {kind: soil,   zone: treatment, sensor_id: SOIL-T1, note: 깊이 10cm}
  soil-treat-02:   {kind: soil,   zone: treatment, sensor_id: SOIL-T2, note: 깊이 20cm}
```

**한 대 더 다는 날은 한 줄이다.** 장치에 `map` 을 적으면 종류의 것 위에
덮이므로, 예비 온습도 센서를 2m 폴대에 달아 기온으로 쓰려면 그 장치만
`map: {temperature: t_air}` 로 덮는다. 종류 없이 장치에 직접 적어도 된다.

같은 구간의 같은 변수를 여러 점이 재면 **중앙값**으로 합친다. 한 점이
고장나거나 국소 그늘에 들어가도 판단이 흔들리지 않게 하려는 것이고, 점 사이
벌어짐(spread)을 센서 이상 신호로 함께 남긴다. 그래서 2점이 설계의 최소다 —
1점이면 그 센서가 죽는 순간 그 구간의 판단이 빈다.

**밸브·차단기는 합치지 않는다.** 밸브 세 개는 세 라인이고 차단기 두 개는 두
회로다. 하나가 열리고 둘이 닫혀 있을 때 중앙값 0 은 '닫혔다'는 거짓이 된다.
이런 변수(`valve_state`·`circuit_state`·유량·전력량 등)는 장치별로 남아
`facility.VALVE-01.valve_state` 처럼 컬럼이 된다. 밸브가 몇 개 붙든 서로를
덮지 않고, 모델 입력으로 새지도 않는다.

**map 을 적지 않으면 `temperature` 는 버려진다.** 같은 필드라도 어디에
달렸느냐에 따라 기온·초관부 온도·지온으로 뜻이 갈리는데, 기본값을 두면
지상 10cm 센서가 조용히 기온으로 들어가 서리 판단이 어긋나기 때문이다.
버릴 때는 수집 로그에 사유를 남긴다.

`state` 도 같다. 밸브의 `state` 는 열림·닫힘이고 차단기의 `state` 는
통전·차단이다. 기본값을 하나 두면 차단기가 조용히 밸브로 들어간다.

```yaml
  valve-treat-01:
    zone: facility
    sensor_id: VALVE-01
    map:
      state: valve_state                  # 열림·닫힘
      flow: irrigation_flow               # 유량 (L/min)
      water_consumed: irrigation_volume   # 적산 수량 -> 구간 차분
      temperature: ""                     # 밸브 몸체 온도. 쓰지 않는다
```

**`state` 가 수집의 핵심이다.** '밸브를 열어라'는 지시를 내렸을 때 정말
열렸는지는 장치가 되읽어 주는 이 값으로만 확인된다. 공인시험 T-07(제어응답)이
보는 것이 바로 그것이고, 지시 기록(`actions`)은 '보냈다'는 사실일 뿐
'실행됐다'는 증거가 아니다.

`energy`·`water_consumed` 는 설치 이후 **누적 총량**이다. 그대로 넣으면
5분 관수량이 수백 L 로 잡히므로 직전 값과의 차이를 쓴다. 적산값은 유량·전류
보다 한 수 위다 — 1분마다 재는 유량계는 30초짜리 관수를 통째로 놓치지만
적산 수량계는 놓치지 않는다.

**역할이 다른 회로는 변수 이름도 다르다.** 관수펌프 회로는
`circuit_state`·`pump_current`, 보조회로(환기·난방)는
`aux_circuit_state`·`motor_current` 다. 제어 논리가 '펌프가 돌았나'를 물을 때
보조회로를 섞어 보면 안 되기 때문이다. 같은 역할의 장치가 여럿(관수 밸브 셋)
인 경우는 위에서 말한 장치별 컬럼이 맡는다.

`sends:` 는 '기본 매핑이 맞아서 적을 것이 없는 필드'를 적는 자리다.
수집에는 영향이 없고(적지 않아도 값은 들어온다), 아래 점검 명령이 '이 장치가
무엇을 보내는가'를 알기 위해 쓴다.

```yaml
  soil-treat-01:
    map:
      temperature: soil_temp
    sends: [soil_moisture, battery, linkquality]
```

받은 메시지는 `data/field/capture/` 에 그대로 쌓인다. 현장에 나가지 않고
같은 자료로 파이프라인을 다시 돌릴 수 있어야 공인시험 재현 절차가
성립한다.

```bash
python scripts/zigbee_bridge.py --replay data/field/capture/capture_20261101.jsonl \
    --out /tmp/replay
```

### WS90 은 Zigbee 가 아니다 (433MHz)

**WS90 자체에는 와이파이가 없다.** 433MHz 송신만 한다. 와이파이를 가진 것은
게이트웨이이고, 그것이 433MHz 를 받아 네트워크로 넘긴다. 그래서 라즈베리파이가
WS90 을 받는 길은 둘이다.

| 경로 | 추가 장비 | 비용 | 특징 |
|---|---|---|---|
| **RTL-SDR 동글** | USB 동글 1개 | ₩3~4만 | 송신 원본 8.8초마다. 중간 장비 없음 |
| **에코윗 게이트웨이 + 와이파이** | GW1200·GW2000 | ₩7~10만 | 일사를 W/m² 로 계산해 줌. 유선(GW2000) 가능 |

**둘 중 하나는 반드시 있어야 한다.** 지금 구매 목록에는 둘 다 없어서 WS90 은
아직 아무 데이터도 보내지 못한다.

**둘을 동시에 켜지는 말 것.** 같은 WS90 을 두 경로로 받아 같은 센서이름으로
쓰면 같은 비가 두 번 들어온다. 강수는 구간 적산이라 두 배가 되고, 그 값으로
관수 판단이 돈다. `configs/devices.yaml` 은 지금 SDR 경로(`rf:`)를 기본으로
두었고 게이트웨이 칸(`ecowitt.gateway`)은 주석 처리돼 있다. 게이트웨이로
가기로 하면 주석을 풀고 `rf:` 의 WS90 줄을 지운다 —
`python -m ofdf.cli sensors` 가 이 어긋남을 찾아 알려 준다.

#### 와이파이 경로 (게이트웨이)

게이트웨이 설정(웹UI 또는 WSView 앱)에서 Customized 업로드를 켠다.

```
Customized        켜기
Protocol Type     Ecowitt
Server / IP       라즈베리파이 주소 (예: 192.168.0.50)
Path              /data/report/
Port              8088
Upload Interval   60 초
```

```bash
python scripts/ecowitt_receiver.py --out data/field --port 8088
```

**바깥 인터넷을 거치지 않는다.** 같은 공유기 안에서만 오가므로 통신이 끊겨도
돌고, 72시간 독립운전 요건과 어긋나지 않는다. 표준 라이브러리만 쓰므로 추가
설치가 없다. 브라우저로 `http://파이주소:8088/` 을 열면 수신 건수가 보인다.

받는 값은 **야드파운드**다. 웹UI 표시 설정과 무관하게 화씨·마일·인치로 오므로
수신기가 환산한다(36.3°F → 2.4℃, 1.57mph → 0.70m/s, 30.07inHg → 1018hPa).

**WS90 의 강수는 `*_piezo` 로 온다.** WS90 은 티핑버킷이 아니라 압전식이라
필드 이름이 다르다 — `dailyrainin` 이 아니라 `drain_piezo`, 강우강도는
`rrain_piezo` 다. 티핑버킷 이름만 받아 두면 강수가 통째로 비는데, 비가 와도
화면에 0 으로 나오므로 아무도 눈치채지 못한다. `srain_piezo` 는 지금 비가
오는지를 0/1 로 주는데, 사업계획서가 요구하는 '강우 감지'가 이것이다.

둘 다 달려 있으면(압전 + 티핑버킷) **앞선 하나만** 강수로 쓴다. 같은 비를
두 번 더하면 구간 강수가 두 배가 되기 때문이다. 쓰지 않은 쪽도 버리지 않고
`rain_alt_total` 로 남겨, 두 계측기가 얼마나 다르게 세는지 따져 볼 수 있게 한다.

**보조 채널도 받는다.** 게이트웨이는 WS90 하나만 받는 것이 아니다. 토양수분
(WH51)·지온(WN34)·온습도(WH31)·엽면습윤(WH35)을 채널 1~8 에 붙일 수 있다.
센서를 한 대 더 사는 날 코드를 고치지 않도록 번호를 일반화해 받고, 어느 구간에
달렸는지는 `configs/devices.yaml` 의 `ecowitt.channels` 에서 읽는다.

```yaml
ecowitt:
  gateway:
    zone: mast
    sensor_id: WS90-01
  channels:
    leaf1:                       # 엽면습윤(WH35) 1번
      zone: treatment
      sensor_id: LW-T1
    th1:                         # 범용 온습도(WH31) 1번
      zone: control
      sensor_id: CN-02
      map:
        t_air: canopy_temp       # 지상 10cm 이므로 기온이 아니다
```

**채널 번호는 센서 계열마다 따로 센다.** `soilmoisture1` 과 `leafwetness_ch1`
과 `temp1f` 은 모두 '1번'이지만 서로 다른 장치다. 번호만 보고 묶으면 셋이 한
센서가 되어 배터리 값이 서로를 덮어쓴다. 그래서 열쇠가 `soil1`·`leaf1`·`th1`
처럼 계열과 번호를 합친 것이다.

범용 온습도계(`temp1f`)는 **설정이 없으면 버린다.** 2m 마스트면 기온이고
지상 10cm 면 초관부 온도라 뜻이 갈리기 때문이다 — Zigbee 의 `temperature` 와
같은 원칙이다. 센서 종류가 이름에 박힌 것(토양수분·지온 프로브·엽면습윤)은
설정 없이도 받되 기본 이름(`ECO-SOIL1` 등)을 쓴다.

> **엽면습윤 센서가 지금 없다.** Ecowitt WH35 를 게이트웨이에 붙이면
> `leafwetness_ch1` 로 바로 들어온다 — 코드는 고치지 않는다.

#### SDR 경로

RTL-SDR 동글과 `rtl_433` 이 직접 받는다. 게이트웨이가 필요 없다.
**구매분은 RTL-SDR Blog V2(R820T2)** 다 — 기본 드라이버로 바로 잡힌다.

```bash
sudo bash scripts/setup_rtlsdr.sh          # ① 설치·그룹·커널 모듈 차단 (한 번)
python scripts/rtl433_bridge.py --check    # ② 동글 → 드라이버 → 디코더 → 수신 순서로 점검
sudo cp deploy/ofdf-rtl433.service /etc/systemd/system/
sudo systemctl enable --now ofdf-rtl433    # ③ 상주 수신
journalctl -u ofdf-rtl433 -f
```

**①이 요점이다.** 라즈베리파이 OS 는 동글을 꽂으면 **TV 수신기로 잡아
버린다**(`dvb_usb_rtl28xxu`). 그러면 `rtl_433` 이 장치를 열지 못해 한 줄도
안 들어오는데 오류도 뚜렷하지 않아 반나절을 잃는다. 스크립트가 그 모듈을
차단하고 내린다.

**②는 막힌 곳에서 멈추고 고치는 법을 적는다.**

```
[✓] USB 동글
      Bus 001 Device 003: ID 0bda:2838 Realtek ... ← RTL2832U
[✓] 커널 DVB 모듈 차단
[✓] Fineoffset-WS90 디코더
[✓] 동글 열기
      Found Rafael Micro R820T tuner
[…] 30초 동안 듣는다 — Fineoffset-WS90 를 기다린다
[✓] WS90 수신
      Fineoffset-WS90 id=12345  3회 (6.0회/분)  RSSI -9.2dB
```

WS90 은 약 9초마다 보내므로 30초에 3회 안팎이 정상이다. 0회면 센서
전원(슈퍼캡)·안테나 위치(**금속 함체 밖**)·거리 순으로 본다. 이웃 장치가
들렸으면 동글은 정상이고 WS90 쪽 문제다. RSSI 가 -20dB 아래면 안테나를
올린다 — 전파가 약해지는 것은 서서히 진행하므로 끊기기 전에 보여야 한다.

안테나: 다이폴 한쪽 다리 **약 16.5cm**(433MHz 1/4파장), USB 연장선으로
함체 밖에 세운다. V2 일부는 MCX 단자라 MCX→SMA 젠더가 필요할 수 있다.

> V4(R828D) 를 쓰게 되면 ①로 부족하다. rtl-sdr-blog 포크 드라이버를
> 소스에서 빌드해야 한다. V2·V3·Nooelec(R820T2) 은 그 과정이 없다.

두 가지가 자동으로 처리된다.

| 문제 | 처리 |
|---|---|
| `rain_mm` 이 **누적값** | 직전 값과의 차이를 쓴다. 값이 줄면(초기화·교체) 그 구간은 0 |
| `wind_max_m_s` 가 **28초 창 최댓값** | `wind_gust_window` 로 따로 받는다 |

**돌풍 이름이 다른 이유.** 사업계획서의 강풍 안전규칙은 3초 순간최대풍속을
기준으로 하는데, WS90 은 2초 간격으로 재어 최근 28초 중 최댓값을 준다.
다른 통계량이라 같은 이름으로 넣으면 농가 화면이 '3초 순간최대'라고 적는데
실제로는 28초 창 값인 상태가 된다. 제어기는 참 3초 계측값이 있으면 그것을
먼저 쓰고, 없으면 이 값으로 물러서되 **조치 사유에 어느 쪽인지 적는다.**

```
[실행] 차광막·피복 즉시 완전 회수(5분 이내) — 순간최대(28초 창)풍속 10.0m/s
```

**이웃 장치가 섞이지 않도록 모델을 걸러 받는다.** 433MHz 는 페어링이 없어서
전파만 받으면 들어온다 — 이웃집 온도계가 수집 파일에 섞이면 품질관리가 통째로
흔들린다. 받을 모델과 설치 위치는 `configs/devices.yaml` 의 `rf:` 칸에서 읽는다.

```yaml
rf:
  Fineoffset-WS90:
    zone: mast
    sensor_id: WS90-01
    note: 폴대 상단 2m
  # 같은 모델이 둘이면 'Fineoffset-WH51/12345' 처럼 id 를 붙여 구분한다
```

토양수분계(WH51)를 추가로 사면 **같은 동글이 그대로 받는다.** `rf:` 에 한 칸
적으면 되고 코드는 고치지 않는다.

> **WS90 이 재지 않는 것.** 엽면습윤·토양수분·EC 는 WS90 에 없다. 환산표에
> 그 이름이 있는 것은 WH35·WH51 을 사면 같은 동글로 들어오기 때문이고,
> 점검 명령은 모델별 구성을 보고 판단하므로 없는 센서를 있다고 적지 않는다.

### RS-485 수질 센서 (있을 때만)

라즈베리파이 하드웨어가 **Shrimp365 수질 모니터링 장비와 같다.** 거기 쓰던
USB-RS485 변환기와 Nengshi 디지털 센서(pH·DO·EC)를 그대로 꽂으면 관수원수·
양액 수질이 들어온다. 프로토콜(MODBUS-RTU 9600 8N1, 기능코드 04, 레지스터
0x0000~16개)·슬레이브 ID(pH 1 · DO 3 · EC 4)·배선이 Shrimp365 와 같으므로
두 장비를 오가며 설정을 바꿀 일이 없다.

```
  [pH 센서 ID1]──┐
  [DO 센서 ID3]──┼── A/B 두 선에 나란히 ──[USB-RS485]──USB──[라즈베리파이]
  [EC 센서 ID4]──┘      센서 전원 DC 9~24V, 0V 는 파이 GND 와 공통
```

**노지 대파 실증에서 수질은 보조 지표라 기본은 꺼짐이다.** 없는 장비를 매
주기 읽으려다 오류를 쌓으면 안 된다. 변환기를 꽂은 뒤:

```bash
python scripts/modbus_bridge.py --scan       # ① 선을 훑어 어느 ID 에 무엇이 있나 (쓰기 없음)
#   configs/devices.yaml 의 rs485: 를 enabled: true 로, sensors: 를 ①대로
python scripts/modbus_bridge.py --check      # ② 지금 한 번 읽어 센서별 상태
sudo cp deploy/ofdf-modbus.service /etc/systemd/system/
sudo systemctl enable --now ofdf-modbus      # ③ 상주. 변환기가 없으면 시작하지 않는다
```

서비스 유닛에 `ConditionPathExists=/dev/ttyUSB0` 가 있어 변환기가 안 꽂혀
있으면 **시작조차 하지 않는다.** 재시작 루프를 돌지 않고 나머지 수집에
영향이 없다.

들어오는 변수는 `water_temp`·`water_ph`·`water_orp`·`water_do`·`water_do_sat`·
`water_ec`(mS/cm = dS/m)·`water_tds`·`water_salinity`(전도도에서 환산). 수온은
세 센서가 다 주지만 **DO 센서 것 하나만** 남긴다 — DO 변환기가 자기 수온으로
포화도를 보정하므로 그 수온이 기록에 있어야 'DO 가 왜 이런가'를 따질 수 있다.
전극이 공중에 있으면 DO 가 포화도 150% 를 넘는데 값은 범위 안이라, 수온으로
포화 농도를 계산해 `range` 로 표시한다.

> 유량·차압 변환기(ID 5·6)도 같은 프로토콜 계열이면 `sensors:` 에 한 줄로
> 켠다. 레지스터 배치는 Shrimp365 와 같은 잠정값이다.

### 무엇이 들어오고 무엇이 안 들어오는지 확인

'모든 센서 데이터를 받는다'는 말은 확인할 수 있어야 한다. 센서를 달고 화면에
뭔가 나오는 것을 보고 끝내면, 빠진 변수는 비가 오는 날이나 서리가 내리는
날에야 드러난다. 그때는 이미 늦다.

```bash
python -m ofdf.cli sensors --devices configs/devices.yaml --field data/field
```

변수마다 상태를 매겨 보여 준다.

| 상태 | 뜻 | 할 일 |
|---|---|---|
| `수신확인` | 수집 파일에 **실제로 값이 들어와 있다** | 없음 |
| `연결됨` | 설정에 적힌 장치가 보내지만 아직 받은 기록이 없다 | 설치·통신 확인 |
| `경로있음` | 매핑은 있는데 그 변수를 보내는 장치가 설정에 없다 | 센서를 달고 설정 한 줄 |
| `대리지표` | 실측 장비가 없어 다른 관측값으로 계산한다 | 정확도 한계를 알고 쓴다 |
| `장비없음` | 받을 길이 없다 | 무엇을 사면 되는지 함께 나온다 |

표는 **매핑표에서 직접 계산한다.** 손으로 적은 목록을 두면 매핑을 고친 날
목록이 틀어지고, 틀어진 목록은 없는 것보다 나쁘다 — 받고 있다고 적혀 있으니
아무도 확인하지 않는다.

표 아래에 두 가지가 더 나온다.

**[측정점]** — 구간·변수마다 센서가 몇 점인지. 1점인 곳에 ▲ 를 붙인다.
그 센서가 죽는 순간 그 구간의 판단이 비는 자리다.

**[미설정 장치]** — 페어링은 됐는데 설정에 없는 장치. 센서를 여러 대
붙이면 반드시 생기는 틈이다. 그 장치의 값은 '모르는 장치'로 버려지는데
화면에는 아무것도 안 나오므로 **센서가 고장난 것과 구별이 안 된다.** 브리지가
Zigbee2MQTT 의 페어링 목록(`bridge/devices`)을 `capture/zigbee_devices.json`
에 남기고, 점검이 그것과 설정을 맞댄다. 모델명이 같이 나오므로 어느 `kind` 로
적을지 바로 안다.

모델을 읽지 않으므로 학습 전에도 돌고, `--json` 으로 기계가 읽을 형식을,
`--strict` 로 장비없음·설정어긋남·미설정 장치가 있으면 종료코드 1 을
받는다(CI 용).

### 센서가 죽은 것을 먼저 안다

화면의 **센서 상태** 칸이 장치별 배터리·전파세기·마지막 수신 시각을
보여준다. 30분 넘게 소식이 없으면 빨간 띠로, 배터리가 20% 이하면 노란 띠로 바뀐다.
WS90 은 배터리를 %가 아니라 전압으로 주므로 태양광 슈퍼캡 전압을 보여주고,
2.6V 이하면 '충전 부족 — 일조 확인'으로 바뀐다. 전파세기도 경로마다 다르다 —
Zigbee 는 `linkquality`(0~255), 433MHz 는 RSSI(dB, 음수)라 숫자의 뜻이 다르므로
단위를 붙여 구분해 보여준다. 흐린 날이 이어지면 전압이
떨어지면서 송신이 끊기는데, 끊긴 뒤가 아니라 떨어지는 중에 보여야 한다. 값이 사라진 뒤에 알면 그 사이 판단은 이미 비어 있었던
것이므로, 농가 화면에 함께 둔다.

센서가 여러 대라 **구간별로 묶어** 보여주고, 구간마다 '몇 대 중 몇 대가
수신 중'인지를 머리에 적는다. 카드를 다 읽지 않아도 어느 구간이 비어 가는지
보이게 하려는 것이다.

밸브 열림·회로 통전·침수 같은 **되읽기 상태**는 같은 칸에 말로 나온다
(`관수 밸브 열림`, `관수 회로 통전`). 이 값들은 평균을 내면 뜻이 사라지므로
마지막 값을 그대로 쓴다 — 밸브가 0.4 만큼 열린 적은 없다.

### 구동부가 덜 들어온 상태로 돌릴 때

`configs/weather.yaml` 의 `edge.installed_devices` 에 **구동부가 실제로 달린
장치만** 적는다. 여기 없는 장치로 가는 조치는 '실행'이 아니라 '권고(농가가
직접)'로 내려가고, 농가 화면에 **'직접'** 으로 표시된다.

적지 않으면 전부 달린 것으로 보고 **실행으로 기록한다.** 실증 기간의 제어
이력이 성능평가의 제어응답 측정 대상이므로, 현장에 내보내기 전에 반드시
맞춰야 하는 값이다.

```yaml
edge:
  installed_devices:
    - 관수밸브
    - 전 구동부        # 스마트 차단기로 회로 차단
    - 해당 구동부
```

구동부가 들어오면 이름을 더하면 된다. 판단 로직은 건드리지 않는다.

### 화면 꺼짐 막기

터치패널은 항상 켜져 있어야 한다. OS 세대에 따라 경로가 다르다.


## 하지 말아야 할 것

- **ONNX 변환본을 쓰지 않는다.** 추론이 70배 빨라지지만 8개 모델 중 4개가
  원본과 다른 등급을 낸다(일치율 99.7~99.9%). 네이티브 LightGBM 이 이미
  목표의 수백 배 여유를 두므로 바꿀 이유가 없다.
- **스레드 수를 늘리지 않는다.** 단일 스레드 바운드라 효과가 없고, 발열만 는다.
- **microSD 에 로그를 쌓지 않는다.** SSD 로 옮기거나 쓰기 주기를 늘린다.
