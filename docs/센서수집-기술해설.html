학습용 문서다. '무엇을 만들었나'보다 '왜 그렇게 만들었나'를 적는다. 코드를 고칠 사람이 이 문서를 읽고 나면, 어느 줄을 왜 건드리면 안 되는지 알 수 있어야 한다. 운영 절차는 라즈베리파이-배포.md, 공인시험은 STA-시험절차서.md 가 맡는다.

1. 왜 수집 경로가 셋인가

구매한 센서가 서로 다른 전파를 쓴다. 한 경로로 몰 수 없다.

경로장치전파라즈베리파이에 꽂는 것파이썬 모듈
ZigbeeTuya 온습도·토양·워터밸브·차단기·누수Zigbee 3.0 (2.4GHz)SONOFF Dongle Plus MG24ofdf.data.zigbee
433MHzEcowitt WS90 7-in-1433.92MHz 전용 RFRTL-SDR 동글ofdf.data.rtl433

WS90 자체에는 와이파이가 없다. 433MHz 송신만 한다. 그래서 받는 길이 둘이고, 둘 중 하나만 쓴다. 둘 다 켜면 같은 비가 두 번 들어와 강수가 두 배가 된다 (§7 설정 어긋남 검출이 이것을 잡는다).

세 경로가 각자 다른 함정을 갖고 있고, 모듈마다 그 함정을 모듈 머리 주석에 적어 두었다.

433MHz페어링이 없어 이웃집 온도계도 들어온다설정의 rf: 에 적은 모델만 받는다

2. 데이터 형식 — 왜 세로(long)인가

모든 경로가 한 가지 형식으로 쓴다.

ts,zone,sensor_id,variable,value,unit,quality
2026-10-14T13:37:00,treatment,CN-T1,canopy_temp,3.1,degC,ok
2026-10-14T13:37:00,treatment,CN-T2,canopy_temp,3.4,degC,ok
2026-10-14T13:37:00,facility,VALVE-01,valve_state,1.0,bool,ok

가로 형식(센서마다 컬럼)이 아닌 이유:

  • 센서를 늘리거나 줄여도 스키마가 바뀌지 않는다. 컬럼을 추가하는 코드가 없다.
  • 결측이 '행이 없음'으로 자연스럽게 표현된다. NaN 을 채워 넣을 일이 없다.
  • 세 경로가 같은 파일 형식을 쓴다. 어느 경로로 왔는지는 sensor_id 가 말한다.

quality 는 버리지 않고 표시만 한다. range 는 물리 유효범위 밖(센서 이상 의심), bad·fault·stale 은 읽을 때 NaN 으로 바꾼다 (field.BAD_QUALITY).

컬럼의 뜻:

컬럼뜻정하는 곳
zone어느 구간인가 — mast·treatment·control·facility설정
sensor_id센서 한 대의 이름 (CN-T1, WS90-01)설정
variable우리가 정한 변수 이름 (canopy_temp) — 장치의 필드 이름이 아니다field.FIELD_VARIABLES
value수치. 상태는 0/1
unit단위. FIELD_VARIABLES 가 정한다

변수 이름이 장치 필드 이름과 다른 것이 핵심이다. 장치는 temperature 라고 보내지만 우리는 t_air·canopy_temp·soil_temp 로 받는다. 이 번역이 §3 의 설정이다.

3. 설정 — configs/devices.yaml

포장에 무엇이 달려 있는지를 한 파일에 적는다. 경로마다 나눠 적으면 한쪽만 고치는 날이 온다. 칸이 넷이다.

kinds:      # 센서 종류별 매핑 (같은 모델 여러 대 → 한 번만 적는다)
devices:    # Zigbee 장치 (Zigbee2MQTT friendly_name 이 열쇠)
rf:         # 433MHz 장치 (rtl_433 의 model 또는 model/id 가 열쇠)
ecowitt:    # 에코윗 게이트웨이와 보조 채널

3.1 뜻이 갈리는 필드는 설정이 말한다

같은 temperature 라도 어디에 달렸느냐에 따라 다른 변수다.

2m 폴대    → t_air        (기온)
지상 10cm  → canopy_temp  (초관부 온도)   ← 서리 판단의 핵심
흙 속      → soil_temp    (지온)
밸브 몸체  → ""           (버린다)

서리 판단은 이 셋을 구분하지 못하면 성립하지 않는다. 그래서 temperature· humidity·state 는 기본값이 없다 (zigbee.AMBIGUOUS_FIELDS). 설정에 적지 않으면 그 값은 버려지고 수집 로그에 사유가 남는다:

[확인 필요] canopy-treat-03.temperature: 장치 종류·설치 위치로 뜻이 갈리는 필드다.
            설정의 map 에 어느 변수인지 적어야 한다

조용히 기본값으로 들어가는 것보다 눈에 보이게 빠지는 것이 낫다. state 도 같다 — 밸브의 state 는 열림·닫힘이고 차단기의 state 는 통전·차단이다.

3.2 종류(kinds)와 장치(devices)

센서는 여러 대 붙는다. 매핑을 장치마다 적으면 토양센서 넉 대에 같은 줄을 네 번 적고, 하나만 고치는 날이 온다.

kinds:
  soil:
    map: {temperature: soil_temp}          # 뜻을 바로잡아야 하는 필드
    sends: [soil_moisture, battery, linkquality]   # 기본 매핑이 맞는 필드

devices:
  soil-treat-01: {kind: soil, zone: treatment, sensor_id: SOIL-T1, note: 깊이 10cm}
  soil-treat-02: {kind: soil, zone: treatment, sensor_id: SOIL-T2, note: 깊이 20cm}
  soil-ctrl-01:  {kind: soil, zone: control,   sensor_id: SOIL-C1}
  • map — 장치 필드 → 우리 변수. 빈 문자열("")은 '버려라'.
  • sends — 수집에는 영향이 없다. §7 점검이 '이 장치가 무엇을 보내는가'를 알기 위해 쓴다. 적지 않아도 값은 들어온다.
  • 장치에 map 을 적으면 종류의 것 위에 덮인다. 예비 온습도계를 2m 에 달아 기온으로 쓰려면 그 장치만 map: {temperature: t_air}.
  • 종류 없이 장치에 직접 적어도 된다.

3.3 설정에 없는 장치

페어링은 했는데 설정에 안 적은 장치의 값은 버려진다 (모르는 장치). 화면에는 아무것도 안 나오므로 고장과 구별이 안 된다. 그래서 브리지가 Zigbee2MQTT 의 페어링 목록(bridge/devices)을 capture/zigbee_devices.json 에 남기고, 점검이 설정과 맞댄다 (§7).

4. 값의 네 가지 종류

장치가 보내는 필드는 성격이 넷이고, 각각 다르게 다룬다.

4.1 측정값 — 그대로

FIELD_VARIABLES 에 있는 변수. 단위와 물리 유효범위가 적혀 있다.

"canopy_temp": ("degC", -25.0, 50.0),
"soil_moisture": ("%", 0.0, 100.0),

범위를 벗어나면 quality=range 로 표시만 한다. 버리는 것은 통합 단계 (reconcile_points)이고, 그마저도 CLAMP_TOLERANCE 안이면 경계로 자른다 — 일사계는 야간에 -20 W/m² 를 정상적으로 내보내는데 이것을 지우면 야간 일사가 통째로 결측이 된다.

4.2 상태값 — 말을 수치로

STATE_WORDS = {"on": 1.0, "off": 0.0, "open": 1.0, "closed": 0.0,
               "detected": 1.0, "clear": 0.0, "wet": 1.0, "dry": 0.0, ...}

zigbee.to_number() 가 참·거짓, 숫자, 상태말을 모두 수치로 읽는다. 모르는 말은 추측하지 않고 None — 밸브 상태를 거꾸로 읽으면 관수했다고 기록하면서 작물은 마른다.

이것이 빠져 있던 것이 가장 큰 구멍이었다. 밸브와 차단기는 자기 상태를 문자열로 보내는데 '숫자가 아니라서' 버려지고 있었다. 명령은 보냈는데 실행됐는지 모르는 상태 — 공인시험 T-07(제어응답)이 묻는 것이 바로 그것이다.

4.3 적산값 — 차분으로

rtl_433   rain_mm          초기화 이후 누적 강수
에코윗     dailyrainin      그날 누적 (자정에 0)
Zigbee    energy           설치 이후 누적 전력량
Zigbee    water_consumed   설치 이후 누적 관수량

그대로 넣으면 5분 강수가 수백 mm 로 잡힌다. ofdf.data.counter.CumulativeCounter 한 곳이 넷을 다 처리한다:

c = CumulativeCounter()
c.step("pump", 10.0)   # 0.0   처음 본 값은 기준점
c.step("pump", 12.5)   # 2.5
c.step("pump", 0.0)    # 0.0   줄어들면(초기화·교체) 그 구간은 0 — 음수를 내지 않는다

적산값은 유량·전류보다 한 수 위다. 1분마다 재는 유량계는 30초짜리 관수를 통째로 놓치지만 적산 수량계는 놓치지 않는다. 30초를 재는 T-07 에서 이것이 결정적이다.

카운터는 메시지 사이에 이어서 세야 한다. 브리지가 하나를 만들어 모든 메시지에 넘긴다 — 메시지마다 새로 만들면 매번 '처음 본 값'이 되어 늘 0 이다.

4.4 진단값 — 따로 남긴다

작물 위험과 무관하지만 자료가 끊기기 전에 알려 주는 유일한 신호.

변수뜻경로
battery_pct / battery_mv / battery_v배터리장치마다 다른 단위로 온다
supercap_vWS90 태양광 슈퍼캡 전압흐린 날 이어지면 떨어지며 송신이 끊긴다
linkquality (0~255) / rssi (dB)전파 세기Zigbee / 433MHz — 숫자의 뜻이 다르다
device_temp차단기 본체 온도과열은 화재 전조

배터리가 떨어지거나 전파가 약해지는 것은 서서히 진행된다. 값이 사라진 뒤가 아니라 사라지기 전에 보여야 하므로 화면의 센서 상태 칸이 이것을 읽는다.

5. 측정점 통합 — 중앙값, 그리고 합치면 안 되는 것

5.1 같은 것을 여러 점에서 재면 중앙값

설계는 구간마다 초관부 온도 2점·토양 2점이다. reconcile_points() 가 같은 (ts, zone, variable) 의 여러 점을 중앙값으로 합친다.

CN-T1 3.0, CN-T2 3.4, CN-T3 9.9   →  3.4   (9.9 에 끌려가지 않는다)

평균이 아닌 이유: 한 점이 고장나거나 국소 그늘에서 벗어나도 판단이 흔들리지 않아야 한다. 점 사이 벌어짐(spread)을 함께 남겨 센서 이상 신호로 쓴다 (spread_alarm).

2점이 설계의 최소다. 1점이면 그 센서가 죽는 순간 그 구간의 판단이 빈다. §7 점검이 1점인 곳에 ▲ 를 붙인다.

5.2 장치마다 다른 것을 재면 합치지 않는다

밸브 세 개는 세 라인이고 차단기 두 개는 두 회로다. 하나가 열리고 둘이 닫혀 있을 때 중앙값 0 은 '닫혔다'는 거짓이다.

PER_DEVICE_VARIABLES = {"valve_state", "circuit_state", "pump_current",
                        "irrigation_flow", "irrigation_volume", ...}

이 변수들은 장치별로 남아 컬럼이 zone.SENSOR.variable 이 된다:

treatment.canopy_temp               ← 2점 중앙값 (구간 컬럼)
facility.VALVE-01.valve_state       ← 장치별 컬럼
facility.VALVE-02.valve_state
facility.PUMP-01.pump_energy

zone_frame() 은 마디가 둘인 컬럼만 모델 입력으로 고른다. 밸브 세 개의 상태가 특징으로 새어 들어가지 않는다.

역할이 다른 회로는 변수 이름도 다르다 — 관수펌프 circuit_state· pump_current, 보조회로 aux_circuit_state·motor_current. 제어 논리가 '펌프가 돌았나'를 물을 때 보조회로를 섞어 보면 안 되기 때문이다.

6. 시간 집계 — 변수마다 다른 셈

'1분 수집·5분 집계', AI 는 1시간 격자. resample() 이 변수 성격대로 모은다.

방식변수이유
sumrain, irrigation_volume, pump_energy양이다. 구간에 얼마나 왔나
mean온도·습도·풍속·유량비율·상태량이다
maxwind_gust_*, rain_detect, valve_state, circuit_state한 번이라도 있었으면 있었던 것

유량은 더하면 안 된다. 1분마다 잰 43 L/min 다섯 개를 더하면 216 L/min — 단위는 L/min 인데 값은 아니게 된다. 구간에 흘러간 양을 묻는 자리는 적산 수량계(irrigation_volume)가 답한다. (끝에서 끝까지 돌려 보다 잡은 버그다.)

상태는 평균을 내면 뜻이 사라진다. 5분 동안 한 번이라도 열렸으면 '열렸다'가 그 구간의 사실이다 — 제어응답 확인은 그것을 묻는다. 밸브가 0.4 만큼 열린 적은 없다.

7. 점검 — "받는다"를 증명하는 법

python -m ofdf.cli sensors --devices configs/devices.yaml --field data/field

'모든 센서 데이터를 받는다'는 말은 확인할 수 있어야 한다. 센서를 달고 화면에 뭔가 나오는 것을 보고 끝내면, 빠진 변수는 비가 오는 날이나 서리가 내리는 날에야 드러난다. ofdf.data.coverage 가 변수마다 상태를 매긴다.

상태뜻근거
수신확인수집 파일에 실제로 값이 있다수집 자료
연결됨설정에 적힌 장치가 보낸다. 아직 받은 기록은 없다설정 × 매핑표 × 모델별 필드
경로있음매핑은 있는데 보내는 장치가 설정에 없다매핑표
대리지표실측 장비가 없어 다른 관측값으로 계산한다PROXY_VARIABLES
장비없음받을 길이 없다. 무엇을 사면 되는지 함께 나온다MISSING_HARDWARE

표는 매핑표에서 직접 계산한다. 손으로 적은 목록을 두면 매핑을 고친 날 목록이 틀어지고, 틀어진 목록은 없는 것보다 나쁘다 — 받고 있다고 적혀 있으니 아무도 확인하지 않는다.

없는 센서를 있다고 적지 않는다. 환산표(RTL433_MAP)에 leaf_wetness 가 있는 것은 WH35 를 사면 같은 동글로 들어오기 때문이지, WS90 이 엽면습윤을 잰다는 뜻이 아니다. 그래서 모델별로 실제로 보내는 필드(MODEL_FIELDS, SENSOR_FIELDS)를 따로 두고, 점검은 그것을 본다. 모르는 모델은 '받는다'고 단정하지 않는다.

표 아래에 셋이 더 나온다.

  • [측정점] 구간·변수별 센서 수. 1점에 ▲.
  • [미설정 장치] 페어링됐는데 설정에 없는 장치, 모델명과 함께.
  • [설정 확인] WS90 을 두 경로로 동시에 받는 등 어긋남.

--json 은 기계가 읽을 형식, --strict 는 문제가 있으면 종료코드 1 (CI 용). 모델을 읽지 않으므로 학습 전에도 돈다.

8. 화면 — 센서 상태 칸

ofdf.cli 의 sensor_status() 가 장치마다 마지막 상태를 data.json 의 sensors 로 내보내고, dashboard/index.html 이 그린다.

  • 구간별로 묶고 '4/4대 수신 중'을 머리에 적는다. 카드를 다 읽지 않아도 어느 구간이 비어 가는지 보인다.
  • 30분 넘게 소식이 없으면 빨간 띠, 배터리 20% 이하·슈퍼캡 2.6V 이하면 노란 띠.
  • 되읽기 상태(관수 밸브 열림, 관수 회로 통전, 침수 정상)를 말로 보여 준다. 마지막 값이다. 색만으로 구분하지 않는다 — 햇빛에 화면이 씻겨도 읽혀야 한다.
  • 전파 세기는 Zigbee linkquality 와 433MHz RSSI(dB) 가 다른 숫자라 단위를 붙여 구분한다.

화면은 별도 서버가 아니다. 판단 서비스가 data.json 을 원자적으로 바꿔 쓰고 브라우저가 30초마다 다시 읽는다. 통신이 끊겨도 같은 기계 안에서 돈다.

9. 공인시험과의 연결

T-07 제어응답 30초 이내. 지시 기록(logs/journal.jsonl 의 actions)은 '명령을 보냈다'는 사실이고, valve_state·circuit_state 는 '장치가 그렇게 됐다'는 사실이다. 시험이 묻는 것은 뒤쪽이다. 측정의 끝점을 이 되읽기 값으로 정했고, 수집 주기가 분해능을 정하므로 시험 중에는 보고 주기를 짧게 둔다.

T-06 저장률·T-08 72시간 독립운전. 받은 원본을 capture/ 에 그대로 남기므로 (--replay) 현장에 나가지 않고 같은 자료로 파이프라인을 다시 돌릴 수 있다. 재현 절차가 이것으로 성립한다.

10. 아직 받을 장비가 없는 것

점검표가 장비없음 으로 알리는 다섯 가지와, 무엇을 사면 되는지.

변수왜 없나사면 되는 것
wind_gust_1s, wind_gust_3sWS90 은 2초 간격 계측이라 28초 창 최댓값(wind_gust_window)만 준다초음파 풍속계(RS-485) 또는 1초 샘플링 풍속계
leaf_wetness엽면습윤 센서가 없다. 대리지표로 계산 중Ecowitt WH35 — 게이트웨이에 붙이면 코드 수정 없이 들어온다
soil_ec구매한 토양센서는 수분·온도만3-in-1(수분·온도·EC) 센서
shade_position차광 구동부 별도 진행구동부와 함께
spray_flow살수 라인 유량계 없음같은 Zigbee 밸브 1대, map: {flow: spray_flow}
emergency_stop비상정지 접점 없음Zigbee 접점 입력 모듈(dry contact)

제어기는 참 3초 계측값이 없으면 wind_gust_window 로 물러서되 조치 사유에 어느 쪽인지 적는다 — 농가 화면이 '3초 순간최대'라고 적는데 실제로는 28초 창 값인 상태를 만들지 않는다.

11. 직접 해 보기 — 기록 되돌리기

현장에 나가지 않고 전체 경로를 돌려 볼 수 있다. 저장된 원본 기록(JSON Lines)을 브리지가 그대로 읽는다.

# 1. Zigbee 기록 → 수집 CSV
python scripts/zigbee_bridge.py --replay data/field/capture/capture_20261014.jsonl \
    --devices configs/devices.yaml --out /tmp/replay

# 2. 433MHz 기록 → 수집 CSV
python scripts/rtl433_bridge.py --replay data/field/capture/rtl433_20261014.jsonl \
    --out /tmp/replay

# 3. 에코윗 기록 → 수집 CSV
python scripts/ecowitt_receiver.py --replay data/field/capture/ecowitt_20261014.jsonl \
    --out /tmp/replay

# 4. 무엇이 들어왔나
python -m ofdf.cli sensors --field /tmp/replay

# 5. 통합·집계를 직접 보기
python - <<'PY'
from ofdf.data import field
raw  = field.read_field("/tmp/replay")          # 세로 형식 그대로
rec  = field.reconcile_points(raw)              # 중앙값 통합 (+ point 컬럼)
wide = field.to_wide(rec)                       # zone.variable / zone.SENSOR.variable
agg  = field.resample(wide, "5min")             # 변수별 sum/mean/max
print(agg.filter(like="facility.VALVE-01").tail())
PY

메시지 한 건을 손으로 넣어 보는 것이 가장 빠른 학습이다:

from ofdf.data import zigbee
devices = zigbee.load_devices("configs/devices.yaml")
unknown = []
rows = zigbee.message_to_rows(
    "zigbee2mqtt/valve-treat-01",
    {"state": "ON", "flow": 14.2, "water_consumed": 141.5, "temperature": 12.5},
    devices, unknown=unknown)
for r in rows: print(r["variable"], r["value"], r["unit"])
print(unknown)      # 비어 있어야 한다 — temperature 는 설정이 ""(버려라)로 답했다

기록 없이도 시험이 같은 것을 한다: tests/test_zigbee.py, test_rtl433.py, test_ecowitt.py, test_field.py, test_coverage.py. 시험 이름이 한국어 문장이라 그 자체가 명세다 — test_밸브가_여럿이면_장치별로_남는다.

12. 코드 지도

src/ofdf/data/
  field.py      변수 목록(FIELD_VARIABLES)·집계 규칙·품질관리·측정점 통합·가로 변환
  counter.py    적산 → 구간 차분. 세 경로가 공유
  zigbee.py     Z2M 메시지 → 세로 형식. 종류/장치 설정, 상태말, 페어링 목록, 화면용 상태
  rtl433.py     rtl_433 JSON → 세로 형식. 모델별 필드, rf: 설정
  ecowitt.py    게이트웨이 POST → 세로 형식. 단위 환산, 압전 강수, 보조 채널
  coverage.py   수집 범위 점검 — 매핑표에서 상태를 계산

scripts/
  zigbee_bridge.py     MQTT 구독 → CSV + capture. bridge/devices 저장
  rtl433_bridge.py     rtl_433 표준출력 → CSV + capture
  ecowitt_receiver.py  HTTP 서버 → CSV + capture

src/ofdf/cli.py        edge(상주) / once / sensors(점검). sensor_status() 가 화면용
configs/devices.yaml   kinds / devices / rf / ecowitt
dashboard/index.html   센서 상태 칸 renderSensors()

고칠 때 지킬 것:

  • 변수를 새로 더하면 FIELD_VARIABLES 에 단위·범위, TIME_AGGREGATION 에 셈, 받을 경로가 없으면 MISSING_HARDWARE 에 설명. 시험이 셋째를 강제한다.
  • 장치 종류를 더하면 kinds: 에 한 칸. 코드는 안 건드린다.
  • 433MHz 모델을 더하면 MODEL_FIELDS 에 실제로 보내는 필드. 없으면 점검이 '받는다'고 단정하지 않는다 — 그게 맞다.
  • AMBIGUOUS_FIELDS 에 기본값을 두고 싶어지면 멈춘다. 그것이 §3.1 이다.

13. 설계를 한 줄로
