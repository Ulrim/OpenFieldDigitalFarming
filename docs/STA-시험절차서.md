# 공인시험 시험절차서 (초안)

노지작물 재해위험 판단·조치추천 AI 현장제어 시제품

| 항목 | 내용 |
|---|---|
| 과제명 | 노지작물 재해위험 판단·조치추천 AI 현장제어 시제품 개발 |
| 사업 | 2026년 AI융합 지능형 농업 생태계 구축 사업 |
| 수행기관 | 주식회사 컬리버 |
| 실증지 | 전라남도 나주시 (노지 대파) |
| 시험 대상 | `ofdf` 0.1.0 (`c0cce1f`) |
| 작성일 | 2026-10-10 |
| 문서 상태 | **초안 — 시험기관 양식 미확인** |

> **이 초안의 전제.** 시험기관 제출 양식을 받지 못한 상태에서 작성했다.
> 공인시험 신청서에 통상 요구되는 구성(시험항목 일람 → 항목별 절차 →

> 표시했다.

## 1. 시험 목적

사업계획서가 정한 정량 성능목표를 **제3자가 같은 입력으로 같은 결과를
재현할 수 있는 형태로** 확인한다.

이 문서는 두 종류의 항목을 명확히 나눈다.

- **지금 시험 가능한 항목** — 공개 관측자료와 시제품 소프트웨어만으로
  재현된다. 현장 설치와 무관하다.
- **현장 설치 후 시험 항목** — 센서·구동부가 들어와야 측정된다. 절차를
  미리 고정해 두고, 설치 후 같은 절차로 측정한다.

섞어서 제출하지 않는다. 설치 전 측정값을 현장 성능인 것처럼 적는 것이
가장 흔한 지적 사유다.

## 2. 시험 대상

### 2.1 구성

| 구분 | 내용 |
|---|---|
| 판단 엔진 | LightGBM, 위험유형 5종 × 예측시계 2종 |
| 모델 파일 | 12개 (3등급 8 + 2등급 전용 4), 합계 약 13 MB |
| 조치 엔진 | 제어 계층 L0~L3, 충돌 해소·중복 방지 |
| 엣지 제어기 | 라즈베리파이, 5분 주기 수집·판단·조치·기록 |
| 현장 화면 | 농가/운영자 2계층, 제어함 터치패널 + 휴대폰 |

### 2.2 위험유형과 예측시계

고온·건조 / 강우·과습 / 병해 유리환경 / 저온·서리 / 복합위험(조합),
각 1시간·3시간. 복합위험은 별도 학습이 아니라 **구성요소에서 조합**한다.

### 2.3 동일성 확인 ※

시험 시작 전 시험기관이 대상물의 동일성을 확인한다.

```bash
git rev-parse HEAD                      # c0cce1f...
sha256sum artifacts/weather/*.txt       # 모델 파일 해시
python -c "from ofdf import __version__; print(__version__)"
```

※ 해시 목록 제출 형식(별지/본문)은 양식에 따른다.

## 3. 시험 환경

### 3.1 소프트웨어 시험 환경

| 항목 | 내용 |
|---|---|
| OS | Linux (x86_64) 또는 Raspberry Pi OS 64-bit |
| Python | 3.11 |
| 주요 의존성 | lightgbm, pandas, numpy, scikit-learn |
| 설치 | `pip install -r requirements.txt` |

### 3.2 시험 데이터

| 구분 | 출처 | 범위 |
|---|---|---|
| 농업기상 시간자료 | 농촌진흥청 농업기상관측 | 나주 5개 지점, 2016~2025 |
| 일자료 | AgERA5 | 나주 격자, 2015~2026 |

**공개 자료만 쓴다.** 시험기관이 같은 자료를 내려받아 독립적으로 재현할
수 있다. 자료 다운로드 절차는 `README.md` §2 에 있다.

### 3.3 데이터 분할

기상사례 블록 단위로 나눈다. 같은 기상 사건이 학습과 시험에 함께 들어가지
않도록 위험 이벤트를 **±12시간 여유를 두고 묶어** 블록으로 만들고, 블록
단위로 배정한다. 위험유형 사이에 같은 분할을 공유하므로 복합위험 조합이
성립한다.

| 구분 | 표본(시간) |
|---|---|
| 학습 | 72,628 |
| 검증 | 16,509 |
| **시험** | **20,063** |

분할 씨앗은 42로 고정한다.

### 3.4 미래 정보 차단

모든 입력 피처는 **판단 시각 이하의 값만** 쓴다. 미래값은 정답에만 쓴다.

일자료(AgERA5)는 **하루 전 값**을 쓴다. 그날 값을 그날 전체에 깔면 01시에
그날 밤의 실현 최저기온을 보게 되어 서리 정답을 미리 보는 셈이 된다.
제어기가 운용 시점에 실제로 가진 것은 어제까지 실현된 일자료다.

※ 시험기관이 이 점을 확인하려면 `src/ofdf/data/dataset.py` 의
`prev_day` 계산과 회귀시험 `tests/test_data.py::test_daily_columns_are_lagged_by_one_day`
를 보면 된다.

## 5. 항목별 시험 절차

### T-01 위험유형별 종합점수 0.80 이상

**목적** — 위험유형 × 예측시계별 판단 정확도가 목표를 충족하는지 확인한다.

**평가 단위** — 정확도가 아니라 **Macro F1** 으로 잰다. 위험사례가 전체의
1% 미만이라 "전부 정상"이라고 답해도 정확도가 99%를 넘기 때문이다.

등급 구분은 **조치가 갈리는지**로 정한다. 주의와 경계가 서로 다른 조치를
내는 유형은 3등급으로, 같은 조치를 내는 유형은 정상 vs 위험 2등급으로
잰다. 이 구분은 임의가 아니라 조치 엔진을 실제로 돌려 확인한 결과다
(`ofdf.evaluation.metrics.operational_score`).

**절차**

```bash
python scripts/train_weather.py \
    --aaos-dir data/raw/aaos \
    --agera5 data/raw/agera5_naju_daily_2015_2026.csv \
    --out artifacts/weather --seed 42
```

**판정기준** — `artifacts/weather/performance.csv` 의 위험유형 × 시계
10개 항목 각각에 대해 조치단위 F1 ≥ 0.80.

**현재 측정값 (참고)**

| 위험유형 | 시계 | 단위 | F1 | 판정 |
|---|---|---|---|---|
| 고온·건조 | 1h | 3등급 | 0.857 | 달성 |
| 고온·건조 | 3h | 3등급 | 0.773 | **미달** |
| 강우·과습 | 1h | 2등급 | 0.903 | 달성 |
| 강우·과습 | 3h | 2등급 | 0.839 | 달성 |
| 병해 유리환경 | 1h | 3등급 | 0.928 | 달성 |
| 병해 유리환경 | 3h | 3등급 | 0.909 | 달성 |
| 저온·서리 | 1h | 2등급 | 0.949 | 달성 |
| 저온·서리 | 3h | 2등급 | 0.923 | 달성 |
| 복합위험(조합) | 1h | 2등급 | 0.878 | 달성 |
| 복합위험(조합) | 3h | 2등급 | 0.759 | **미달** |

**10개 중 8개 달성.** 미달 2건을 감추지 않는다. 고온·건조 3시간과
복합위험 3시간이 목표에 못 미친다.

### T-02 위험 놓침 방지율 85% 이상

**목적** — 실제 위험을 놓치지 않는지 확인한다. 재해 경보에서 **가장
중요한 지표**다. 오경보는 농가가 한 번 헛걸음하는 비용이지만, 놓침은
작물 피해로 직결된다.

**절차** — T-01 과 같은 실행에서 산출된다.

**판정기준** — 10개 항목 각각 `AI 놓침방지율` ≥ 0.85.

**현재 측정값** — **10개 전부 달성** (최저 0.894, 복합위험 3시간).

---

### T-03 단순 기준값 대비 5%p 이상 개선

**목적** — AI 가 단순 임계값 규칙보다 나은지 확인한다.

**비교 대상** — 사업계획서 기준표를 그대로 코드화한 임계값 규칙
(`ofdf.models.baseline`). 같은 시험 자료, 같은 평가 단위로 잰다.

**⚠ 합의가 필요한 사항 ※** — "5%p 개선"을 **무엇으로 재는지**가
사업계획서에 명시돼 있지 않다. 두 해석에서 결과가 다르다.

| 기준 | 달성 |
|---|---|
| 조치단위 F1 | 일부 항목 |
| 놓침 방지율 | 전 항목 (규칙이 위험의 40% 이상을 놓친다) |

규칙은 **현재 센서값이 임계를 넘은 뒤에** 작동하므로 선행 경보를 구조적으로
낼 수 없다. 규칙의 놓침 방지율은 강우·과습 3시간 0.600, 복합 3시간 0.567
이다. AI 는 정밀도를 내주고 재현율을 가져온다(각 0.903, 0.894).

사업계획서가 1순위로 둔 지표가 '위험 놓침 방지율'이므로 **놓침 방지율
기준으로 재는 것이 타당**하다고 보나, 시험 접수 전 발주기관과 확정해야
한다.

### T-04 AI 판단 30초 이내

**목적** — 판단 1회가 목표 시간 안에 끝나는지 확인한다.

**측정 구간** — 모델 추론만이 아니라 **센서 입력 → 파생변수 → 시계열
피처 202개 → 위험유형 5종 추론 → 복합위험 조합 → 판단근거 추출 → 조치
결정 → 이력 기록** 전부를 잰다. 추론만 재면 실제 응답보다 훨씬 짧게
나온다.

**절차**

```bash
OMP_NUM_THREADS=1 python scripts/benchmark_inference.py \
    --cache artifacts/dataset.pkl --models artifacts/weather \
    --out artifacts/benchmark
```

**판정기준** — 끝에서 끝까지 **평균** 30초 이내. 참고로 p95·최대도 함께
기록한다.

**현재 측정값 (x86_64 서버)**

| 구성 | 평균 | p95 | 최대 |
|---|---|---|---|
| 1코어 고정 | 33.6 ms | 46.0 ms | 72.1 ms |
| 4코어 | 37.8 ms | 65.9 ms | 101.3 ms |

목표 대비 약 **890배 여유**다. 코어를 늘려도 빨라지지 않는다(단일 스레드
바운드).

**제어기에서 재측정 필요** — 위 값은 x86_64 기준이다. 라즈베리파이는
코어당 성능이 낮으므로 반입 후 같은 명령으로 다시 재고, 그 값을
성적서에 싣는다.

### T-05 핵심 실증 시나리오

**목적** — 사업계획서가 정한 시나리오에서 판단·조치가 규정대로 동작하는지
확인한다.

**구분 표기** — 각 시나리오는 **입력모사**인지 **자연사례**인지 반드시
표기한다. 현재는 전부 입력모사다. 실증 기간 중 자연 발생 사례가 쌓이면
같은 판정기준으로 다시 잰다.

**절차**

```bash
python scripts/run_scenarios.py --out artifacts/scenarios
```

**시험 항목 (12종)**

| # | 시나리오 | 반복 | 최소 통과 |
|---|---|---|---|
| 1 | 강우·과습 관수중단 | 10 | 10 |
| 2 | 저온·서리 사전경보 | 10 | 10 |
| 3 | 다습·병해 유리환경 알림 | 10 | 10 |
| 4 | 복합: 강우 후 저온다습 | 10 | 10 |
| 5 | 복합: 과습 + 서리 | 10 | 10 |
| 6 | 고온·건조 제한운영 | 20 | 19 |
| 7 | 강풍 안전보호 | 10 | 10 |
| 8 | 통신장애 ① 단기 두절·복구 | 3 | 3 |
| 9 | 통신장애 ② 장기 두절(독립운전 지속) | 3 | 3 |
| 10 | 통신장애 ③ 간헐 두절(플래핑) | 3 | 3 |
| 11 | 통신장애 ④ 복구 후 이력 동기화 | 3 | 3 |
| 12 | 통신장애 ⑤ 두절 중 안전사건 | 3 | 3 |

**통신장애 5종에 관하여 ※** — 사업계획서는 '통신장애 5종 시나리오'를
요구한다. 위 ①~⑤는 서로 다른 고장 양상으로 옮긴 것이며, **사업계획서의
5종과 1:1로 대응하는지는 원문 대조가 필요하다.** 대조 결과에 따라 이름과
구성을 조정한다.

⑤가 가장 중요하다. 통신이 살아 있을 때만 안전규칙이 동작한다면 그것은
안전장치가 아니다.

**판정기준** — 12종 전부 '적합'.

**현재 결과** — 12/12 적합.

### T-06 데이터 정상 수집·저장률 98% 이상 *(센서 설치 후)*

**목적** — 현장 자료가 빠짐없이 들어오고 남는지 확인한다.

**산출 방법** — 두 가지를 **따로 세어 곱한다.** 서로 다른 고장이기
때문이다.

| 구분 | 세는 것 | 잡아내는 고장 |
|---|---|---|
| 수집률 | 기대 시각 × 측정점 × 변수 격자 대비 실제 값 | 센서 고장, 통신 두절 |
| 저장률 | 제어기가 돈 주기 대비 판단 이력이 남은 비율 | 기록 유실 |

**절차**

```bash
python scripts/measure_availability.py \
    --field data/field --journal logs/journal.jsonl \
    --start 2026-11-01T00:00:00+09:00 \
    --end   2026-11-08T00:00:00+09:00 \
    --out artifacts/availability.json
```

**⚠ 시험 구간을 반드시 지정한다.** `--start`/`--end` 를 주지 않으면
**자료가 있는 구간만** 분모로 잡혀, 수집기가 아예 죽어 있던 시간이 빠진 채
100%가 나온다. 시험기관이 정한 시험 구간 전체를 분모로 넣어야 한다.

**판정기준** — 수집·저장률 ≥ 0.98. 더불어 가장 긴 결측 구간을 함께
기록한다.

**기록 양식** — 산출 JSON 에 기대표본·관측표본·변수별 수집률·결측 구간이
들어간다. 성능평가서가 이를 그대로 싣는다.

### T-07 제어 응답 30초 이내 *(구동부 설치 후)*

**목적** — 판단이 난 뒤 실제 장치가 동작을 마치기까지의 시간을 잰다.

**⚠ 현재 시험 불가 — 구동부 미설치.** 조치 엔진이 명령하는 장치 7종
가운데 1차 구매분이 덮는 것은 관수밸브와 전원차단뿐이다. 차광막·야간피복·
살수 구동부와 카메라는 별도 발주다.

제어기 설정(`configs/weather.yaml` 의 `edge.installed_devices`)에 달린
장치만 적어 두면, 없는 장치로 가는 조치는 '실행'이 아니라 **'권고(농가가
직접)'** 으로 기록된다. 없는 장치를 실행으로 적으면 이 항목의 측정값이
틀어진다.

**설치 후 절차 (예정)**

1. 판단 이력(`logs/journal.jsonl`)에서 명령 발행 시각을 읽는다.
2. 해당 장치의 동작 완료 신호(밸브 유량 변화, 차광막 위치값) 시각을 읽는다.
3. 두 시각의 차이를 명령별로 집계한다.

**판정기준** — 평균 30초 이내. 차광막 완전 회수는 별도로 **5분 이내**
(강풍 안전규칙 기준).

※ 측정 구간의 시작점을 '판단 완료'로 할지 '명령 발행'으로 할지 시험기관과
확정한다.

### T-08 로컬 독립운전 72시간 *(제어기 설치 후)*

**목적** — 서버 통신이 끊긴 채로 수집·판단·제어·기록이 유지되는지
확인한다.

**현재 상태** — 설계와 코드는 있고 입력모사 시험(T-05 ⑧~⑫)을 통과한다.
**실제 72시간 차단 시험은 제어기 설치 후**다.

**설치 후 절차 (예정)**

1. 제어기를 정상 운전 상태로 두고 서버 통신을 물리적으로 차단한다.
2. 72시간 유지하며 5분 주기 판단이 계속되는지 확인한다.
3. 차단 중 전원을 n회 끊었다 넣어 재부팅 후 이어서 도는지 확인한다.
4. 통신을 복구하고 쌓인 판단 이력이 시간순으로 올라가는지 확인한다.
5. 유실 건수를 자동 집계한다(T-06 의 저장률과 같은 산출).

**판정기준** — 72시간 동안 판단 중단 없음, 이력 유실 0건, 복구 후 동기화
완료.

**예상 자료량** — 5분 주기 72시간 = 864건, 건당 약 1.6 KB → 약 1.4 MB.
저장공간은 제약이 아니다.

## 6. 재현 절차 (전체)

시험기관이 처음부터 끝까지 다시 돌리는 순서다.

```bash
# 1. 환경
python3 -m venv .venv && . .venv/bin/activate

# 3. 소프트웨어 자체 시험 (회귀시험)

    --agera5 data/raw/agera5_naju_daily_2015_2026.csv \
    --out artifacts/weather --seed 42

python scripts/run_scenarios.py --out artifacts/scenarios

    --cache artifacts/dataset.pkl --models artifacts/weather \
```
